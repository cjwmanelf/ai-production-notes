01 / DESIGN

서비스 설계: 답이 나온 다음을 생각하기

그럴듯한 답을 한 번 만드는 것과, 사용자가 내일 다시 찾아오는 것은 다른 문제다. 출발점은 모델 선택보다 사용자가 그 답을 어디에 쓰는지에 있다.

가상의 ‘학습 회고 도우미’를 떠올려 보자. 학습자가 강의 뒤에 필기를 넣으면 핵심 개념과 복습 질문을 받고, 다음 날 휴대폰으로 다시 읽는 서비스다. 이때 중요한 요구는 요약의 길이만이 아니다. 어제 만든 결과를 다시 찾을 수 있어야 하고, 원문에 없는 설명을 구분할 수 있어야 하며, 잘못된 요약을 고칠 수 있어야 한다. 누가, 언제, 어떤 도구에서 시작하고 결과로 무엇을 할지를 먼저 적으면 필요한 화면과 저장 대상이 드러난다.

처음부터 웹앱이 필요한지도 이 맥락으로 판단한다. 혼자 복습한다면 기성 AI 도구로 충분할 수 있다. 계정이 없는 사람에게 제공하거나 사용량과 접근 권한을 직접 관리해야 한다면 웹앱으로 옮길 이유가 생긴다. 사용자에게 “쓰겠어요?”라고 묻기보다 최근에 필기를 어떻게 정리했는지 확인하는 편이 요구사항의 근거를 얻기 좋다. 아직 확인하지 못한 내용은 PRD에 가정으로 남긴다.

기다림과 실패도 요구사항이다

짧은 작업은 요청 안에서 답을 기다리는 동기 처리로 시작할 수 있다. 긴 문서 여러 개를 처리한다면 작업 ID를 먼저 돌려주고 상태를 조회하는 비동기가 더 알맞을 수 있다. 매일 아침 복습 질문을 보내는 일은 스케줄 실행에 가깝다. 스트리밍은 답이 나타나는 시간을 앞당기지만 전체 작업을 끝내 주지는 않는다. 답을 보낸 뒤 저장이나 기억 정리가 이어진다면 그 시간까지 관측해야 한다.

PRD 한 장에는 이 흐름뿐 아니라 누가 자료를 볼 수 있는지, 외부 모델에 무엇을 보내는지, 얼마나 보관하는지, 비용 한도와 파일럿 판단 기준을 담는다. 답에 근거를 붙이고 학습자가 수정하게 하는 것도 기능이다. 자료가 부족한 상황에서는 확신에 찬 답 대신 부족함을 표시하도록 정해야 한다. 설계 문서는 코딩 에이전트에 줄 주문서이면서, 나중에 가정과 실제를 비교할 기준이 된다.

02 / REPRODUCIBILITY

재현 가능한 배포: 확인한 것을 내보내기

배포의 핵심 질문은 “주소가 열리는가”에서 “어떤 코드와 환경이 실행 중인가”로 바뀐다.

Cloud Run을 이해할 때는 소스, 빌드, 이미지 저장소, 리비전, 실행 인스턴스를 구분하면 길이 보인다. 이미지는 코드와 런타임, 필요한 패키지를 묶은 실행 재료이고 컨테이너는 그것을 실행한 상태다. 필기 사진을 읽는 기능에 시스템 OCR 프로그램이 필요하다면, 내 컴퓨터에 설치돼 있다는 사실만으로 서버에서도 작동하지는 않는다. Dockerfile에 실행 환경을 기록해야 같은 문제를 다시 설명하고 재현할 수 있다.

자동 배포도 곧 품질 보장은 아니다. PR의 CI는 시간대나 입력 검증처럼 반복해서 확인할 규칙을 검사하고, staging에서는 실제 사용 흐름을 확인한다. 페이크 LLM을 쓰는 테스트는 빠르고 일정하지만 실제 모델의 답변 품질을 보장하지 않는다. 테스트가 초록색이어도 제출 버튼이 사라진 화면은 사람이 직접 써 보거나 별도의 화면 검사로 찾아야 한다.

같은 커밋보다 더 강한 연결

staging과 production에서 같은 커밋을 각각 빌드하면 의존성이나 빌드 환경 때문에 서로 다른 결과물이 나올 수 있다. 한 번 만든 이미지를 검증하고 그 다이제스트를 지정해 승격하면 “확인한 이미지가 운영에 갔다”는 연결을 만들 수 있다. 태그는 사람이 찾기 편한 이름이고, 다이제스트는 이미지 내용의 식별자다. 커밋, 이미지, 리비전, 버전 응답을 함께 기록하되 승인 대기 중 staging이 바뀌어도 승인한 대상이 달라지지 않도록 고정한다.

환경마다 API 키와 DB를 분리하고 시크릿은 이미지나 저장소에 넣지 않는다. 배포 권한과 실행 중 필요한 권한도 나누어야 한다. 배포 오류가 “포트가 열리지 않았다”라고 끝나더라도, 원인은 그보다 앞선 컨테이너 로그의 키 누락일 수 있다. 마지막 오류 문구만 수정하는 대신 처음 실패한 지점부터 읽는 습관이 실행 환경과 애플리케이션 문제를 가른다.

03 / SAFE ROLLOUT

안전한 전환: 새 버전으로 가는 길, 돌아오는 길

회고 결과를 컨테이너 메모리에만 두면 배포나 인스턴스 교체가 곧 데이터 유실이 된다. 서버를 늘리거나 갈아 끼우려면 지속해야 할 상태를 외부 DB에 두어야 한다. 여기서 무상태란 서비스에 데이터가 없다는 뜻이 아니라, 요청을 처리하는 서버 한 대에만 의존하는 상태를 줄인다는 뜻이다.

두 버전이 동시에 같은 DB를 사용하는 순간에는 데이터 구조의 호환성이 중요해진다. 새 버전에 맞춰 열을 바로 삭제하면 이전 버전으로 트래픽을 되돌려도 복구되지 않을 수 있다. 따라서 롤백 가능성은 이전 이미지 보관, DB 변경 순서, 종료 중인 요청 처리까지 함께 설계해야 생긴다.

트래픽 전환 방식의 차이
방식전환 방법판단할 것
블루그린준비한 새 버전으로 요청 대상을 전환전환 전 준비 상태와 되돌릴 버전
카나리일부 요청부터 보내며 비율 확대오류·지연·답변 품질과 충분한 관측량

프로세스가 포트를 열었다고 서비스가 준비된 것은 아니다. 스타트업 프로브는 실제 준비 조건을 확인해야 하고, 종료 신호를 받은 프로세스는 처리 중인 요청을 정리할 수 있어야 한다. Cloud Run이 리비전과 트래픽 전환을 제공해도 준비 기준과 앱의 종료 동작은 서비스 쪽에서 정할 부분이다. health check 통과는 답이 정확하다는 증거와도 다르다.

안정 버전 90%새 버전 10%

새 버전에 요청의 10%를 보내는 가상 예시입니다. 오류와 지연, 답변 품질을 확인한 뒤 확대 여부를 결정합니다.

요청이 적을 때 10%라는 비율만으로 안전성을 판단하기는 어렵다. 한동안 오류가 없었던 것이 충분히 검증됐다는 뜻은 아니다. 관측할 요청 수와 시간, 중단 조건을 먼저 정하고 새 버전이 답을 잘못 만들 때도 전환을 멈출 수 있어야 한다. 이 지점에서 배포 기술은 관측과 평가로 이어진다.

04 / OBSERVE & EVALUATE

관측과 평가: HTTP 200 뒤에 숨은 실패

요청이 성공했는데 요약은 틀릴 수 있다. 빨리 끝났는데 중요한 근거를 빠뜨릴 수도 있다.

Langfuse 같은 관측 도구에서 trace는 한 요청의 흐름을, span은 검색이나 저장 같은 단계를, generation은 모델 호출의 입력·출력과 토큰 사용량을 살피는 단위를 제공한다. 무엇을 기록할지는 “어떤 질문에 답해야 하는가”에서 거꾸로 정한다. 회고 도우미라면 문서 검색 결과, 요약에 전달한 근거, 실제 답을 이어 볼 수 있어야 근거가 처음 사라진 곳을 찾는다.

TRY 02 / 가상 TRACE

같은 성공 응답, 서로 다른 문제

가상 trace · 정상 응답

문서 검색
0.3초
요약 생성
1.2초
결과 저장
0.2초

문서 검색 0.3초, 요약 생성 1.2초, 결과 저장 0.2초인 가상 요청입니다. 답이 올바른지는 시간 막대와 별도로 근거 문서에 대조해 확인해야 합니다.

모든 기록은 설명을 위한 가상 데이터다. 느린 응답은 요약 생성만 4.8초로 늘어난다. 잘못된 답은 정상과 시간이 같아 속도만으로는 구별할 수 없다.

관측과 평가는 연결되지만 역할이 다르다. 관측은 어떤 단계에서 무엇이 일어났는지를 보여 주고, 평가는 그 결과를 미리 정한 기준으로 판정한다. 오류를 찾을 때도 마지막 답만 보지 않는다. 올바른 문서를 못 찾았는지, 찾은 내용을 모델에 전달하지 않았는지, 전달했는데 다르게 답했는지를 나누어야 검색·코드·프롬프트 중 고칠 곳이 보인다.

고친 답과 원래 맞던 답을 함께 보기

실패 사례만 모으면 수정한 유형의 점수는 좋아져도 기존의 좋은 답이 나빠진 사실을 놓친다. 정상 사례를 함께 넣고 같은 데이터셋과 평가자로 버전을 비교한다. 필수 필드나 정확한 계산처럼 판정이 명확한 항목은 코드로 검사하고, 원문 충실성처럼 읽어야 판단할 항목은 기준을 적어 LLM 심사나 사람 검토에 맡긴다. LLM 심사도 정답은 아니다. 사람의 판정과 맞는지 검증하고 판단 이유를 읽어야 한다.

환경과 코드·프롬프트 버전을 기록하면 업데이트 전후를 나누어 볼 수 있다. 단 한 번의 점수 차이로 개선을 선언하지 않고 응답의 변동성도 확인한다. “별로예요”는 먼저 읽을 요청을 고르는 신호이지 전체 불만족률이 아니다. 버튼을 누르지 않는 사용자와 정정·재질문 같은 행동도 살피고, 문제의 빈도는 전체 관측 범위에서 다시 센다. 기록에 원문이 포함된다면 수집 범위, 마스킹, 보관 기간과 접근 권한도 먼저 정한다.

05 / SUSTAINABILITY

지속 가능한 서비스: 한 번의 답에 숨은 비용

사용자는 메시지를 한 번 보냈지만 서비스는 분류, 답변 생성, 기억 정리 등으로 모델을 여러 번 부를 수 있다. 따라서 메시지당 원가는 한 번의 LLM 호출 가격이 아니라 관련 호출 비용의 합으로 보아야 한다. 평균뿐 아니라 긴 대화나 비싼 요청의 분포를 살펴야 무료 한도와 사용자별 사용량을 정할 근거가 생긴다.

TRY 03 / 비용 가정 바꾸기

작은 단가도 사용량과 함께 커진다

1,000

월 변동원가 90,000원

1,000건 × 30일 × 3원 = 90,000원

매일 같은 요청 수로 30일 사용하고, 메시지당 모든 LLM 호출을 합한 변동원가를 가상 값 3원으로 가정했습니다. 고정비·세금·결제수수료는 제외합니다. 단가는 설명을 위한 가정입니다.

최대 인스턴스 수는 동시에 처리하는 양을 제한하지만 장기간의 LLM 지출 총액을 막지는 않는다. 예산 알림 역시 자동 차단과 다르다. 사용자별 한도와 모델 제공사의 사용 한도를 구분해 설계하고, 모델이나 문맥 길이를 줄여 비용을 아끼려면 품질 평가를 다시 거쳐야 한다. 싸진 답이 학습에 도움이 되지 않는다면 목적을 잃는다.

돈과 배포 채널에도 상태가 있다

유료 크레딧을 붙인다면 잔액 숫자만 덮어쓰기보다 충전·차감 기록을 원장으로 남긴다. 서버가 주문의 소유자와 금액을 확인하고 승인한 뒤 지급하며, 같은 요청이 다시 와도 한 번만 처리하도록 멱등키와 유일한 거래 참조를 둔다. 승인 뒤 기록 실패나 동시 차감도 별도로 다뤄야 한다. 결제 성공 화면 하나가 돈의 흐름 전체를 증명하지는 않는다.

휴대폰에서 복습하게 하려면 화면을 옮기는 것과 출시를 나누어 생각한다. Expo 개발 실행은 빠르게 확인하는 단계, 앱 빌드는 설치할 결과물을 만드는 단계, 스토어 제출은 심사와 공개를 준비하는 단계다. 백엔드는 재사용할 수 있지만 앱에는 비밀 키를 넣지 않는다. 웹과 앱에서 같은 학습 기록을 보게 할 계정 연결, 데이터 삭제, 신고와 결제 정책은 출시 전에 별도로 검토할 항목이다. 기기에서 한 번 열렸다고 운영 준비가 모두 끝난 것은 아니다.

적용과 회고: 다음 수정의 근거 남기기

이 과정을 하나로 묶는 것은 도구의 개수가 아니라, 다음 결정을 설명할 수 있는 기록이다.

가상 회고 도우미의 첫 운영 계획이라면 범위를 작게 잡겠다. 먼저 필기 입력과 결과 재열람이라는 한 흐름을 검증하고, 외부 저장소와 접근 제어를 붙인 뒤 같은 이미지를 staging에서 확인한다. 그다음 트래픽 전환과 롤백을 연습하고, 검색·생성·저장을 계측한다. 결제와 모바일 확장은 이 기본 흐름의 필요성과 비용을 확인한 다음 결정하는 순서다.

예를 들어 “원문에 없는 내용을 요약에 섞는 문제”를 개선 대상으로 고를 수 있다. 결과를 본 뒤 유리한 기준을 붙이지 않도록 실험 전에 판정 문장과 내보낼 조건을 적는다. 아래 수치는 첫 파일럿을 시작할 때 사용할 수 있는 합격 기준의 예시다.

가상 파일럿의 합격 기준 제안
확인 대상사전에 적을 제안 기준남길 근거
근거 충실성실패 유형 20개 중 18개 이상 통과문장별 근거 대조와 평가 이유
회귀 여부정상 사례 20개의 통과 수가 기존보다 감소하지 않음같은 데이터셋의 버전별 결과
응답 시간동일 조건 100회에서 전체 처리 시간 p95 8초 이하저장 완료까지의 trace 시간
배포 전환전환 중 점검 요청 100회 실패 0건요청 결과와 리비전 기록

p95는 관측 요청의 95%가 그 시간 안에 끝났다는 뜻입니다. 작은 표본에서 실패가 없었다고 실제 운영의 무장애를 보장할 수는 없습니다. 평가 반복 횟수와 관측 조건을 함께 기록하고, 새 표현과 실제 사용 패턴으로 확인 범위를 넓혀야 합니다.

  1. 모으기

    트레이스와 피드백을 모으고 수집 범위를 기록한다. 운영 기록이 부족해 직접 만든 대화는 실제 사용자 기록과 구분한다.

  2. 찾기

    정정한 턴, 반복 질문, 느리거나 비싼 요청에서 문제 후보를 찾는다. 이상한 답 하나로 결론 내리지 않고 다른 기록에서도 반복되는지 확인한다.

  3. 고르기

    후보의 빈도, 사용자에게 미치는 영향, 수정 비용을 비교해 하나를 고른다. 무엇을 먼저 고치기로 했는지 이유를 남긴다.

  4. 고치기

    문제와 정상 사례를 묶고 한 가지를 바꾼다. 같은 평가 조건에서 전후를 비교하며 프롬프트로 고칠 일과 코드로 고칠 일을 구분한다.

  5. 확인하기

    배포 후에는 외운 문장을 다시 보내는 데 그치지 않는다. 표현을 바꾼 새 대화를 보내고 버전별 품질·지연·비용을 함께 읽어 유지하거나 되돌린다.

좋은 회고는 “잘됐다”는 말보다, 무엇을 근거로 다음 변경을 선택했는지를 남긴다.

이번 모듈에서 가장 중요하게 정리한 관점은 기록과 판단의 연결이다. 설계는 사용 맥락을 기록하고, 배포는 실행 대상을 기록하며, 관측은 실제 흐름을 기록한다. 평가는 그 기록을 판단 기준에 연결한다. 아직 확인하지 못한 것은 가정으로 남겨 두고, 한 번의 개선마다 비교 가능한 근거를 더하는 것. 데모가 계속 쓰는 서비스가 되는 과정은 이 작은 반복에 가깝다.
